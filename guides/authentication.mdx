Private endpoints on `https://gateway.bit2me.com` require an API key **and** the matching **secret**. You create both in [Get API keys](https://account.bit2me.com/api-keys). The secret is shown once; it is what you HMAC with. Never share a key or secret.

There is **no sandbox host**. Wallet, Pro, Partner, Embed, and gateway all use production URLs (`gateway.bit2me.com`, `embed.bit2me.com`). Integration testing uses your live keys with the smallest scope and an IP allowlist.

<Warning>
If requests fail with 401, sync the machine clock with NTP first. The documented nonce window is 5 seconds of clock skew against Bit2Me UTC. Check [status.bit2me.com](https://status.bit2me.com) before you assume a platform outage. If this persists, [open a support ticket](https://support.bit2me.com/en/support/tickets/new).
</Warning>

## Headers

| Header | Required | Description |
| --- | --- | --- |
| `x-api-key` / `X-API-KEY` | Yes (private) | Public API key |
| `x-nonce` | Yes (signed) | Unix time in **milliseconds** (`Date.now()`). Clock-skew window: **5 seconds** |
| `api-signature` | Yes (signed) | HMAC described below |
| `X-SUBACCOUNT-ID` | When acting for an end user | Subaccount `userId`. HTTP names are case-insensitive; samples use this spelling |
| `x-totp` | Sensitive operations | 6-digit 2FA code |
| `x-totp-type` | With `x-totp` | `gauth`, `sms`, or `email`. **Always `gauth` for subaccounts** |

Validate the server TLS certificate and abort if validation fails.

## HMAC algorithm

1. Build the message:
   - No body: `{nonce}:{path}`
   - JSON body: `{nonce}:{path}:{compactJson}`
2. SHA-256 the message (binary digest).
3. HMAC-SHA512 using your **secret**, over that digest.
4. Base64-encode the HMAC. That value is `api-signature`.

The body used to sign **must** be the exact request body string:

- JavaScript: `JSON.stringify(body)` (no spaces).
- Python: `json.dumps(body, separators=(",", ":"))`.

Do not mix pretty-printed JSON into the signature. Do not POST `{}` on no-payload calls: an empty object is still a body and would be signed as `{}`. That includes `POST /v1/signin/apikey` when you are not sending `userId` — omit the body (and sign `{nonce}:{path}`), or send a real JSON object and sign that object.

<CodeGroup>
```javascript Node.js
const crypto = require("crypto");

function getClientMessageToSign(nonce, url, body) {
  const hasBody = !!body && Object.keys(body).length > 0;
  return hasBody ? `${nonce}:${url}:${JSON.stringify(body)}` : `${nonce}:${url}`;
}

function getMessageSignature(message, secret) {
  const hashDigest = crypto.createHash("sha256").update(message).digest("binary");
  return crypto.createHmac("sha512", secret).update(hashDigest, "binary").digest("base64");
}

const nonce = Date.now();
const path = "/v1/trading/wallet/balance";
const signature = getMessageSignature(getClientMessageToSign(nonce, path), process.env.BIT2ME_API_SECRET);
```

```python Python
import hashlib, hmac, json, base64

def sign(nonce: str, path: str, secret: str, body=None) -> str:
    if body is None:
        message = f"{nonce}:{path}".encode()
    else:
        compact = json.dumps(body, separators=(",", ":"))
        message = f"{nonce}:{path}:{compact}".encode()
    digest = hashlib.sha256(message).digest()
    return base64.b64encode(hmac.new(secret.encode(), digest, hashlib.sha512).digest()).decode()
```

```bash cURL
# Replace SIGNATURE after computing HMAC locally.
curl -sS "https://gateway.bit2me.com/v1/trading/wallet/balance" \
  -H "x-api-key: $BIT2ME_API_KEY" \
  -H "api-signature: $SIGNATURE" \
  -H "x-nonce: $NONCE"
```
</CodeGroup>

## Which operations are signed

OpenAPI marks private operations with `ApiKeyAuth`. That is the HMAC pair (`x-api-key` + `api-signature` + `x-nonce`), not “API key only”.

| Signed | Not signed |
| --- | --- |
| Every private Wallet / Partner / Pro REST call, including `POST /v1/signin/apikey` | Public Pro market data (`GET /v1/trading/market-config`, candles, book, tickers) |
| Widget session: `POST /v1/signin/apikey` with `{ "userId": "<subaccount>" }` | `POST /v1/signin/embed` — different contract (token exchange). Do not send your API key there |

The REST playground cannot compute HMAC. Copy the example, sign locally, send from your backend. A working first call: [Quickstart](/quickstart) (`GET /v1/wallet/pocket`).

## Invalid credentials (403)

Some gateway routes, including HMAC sign-in and Pro Wallet funding, return **403** `invalid credentials` for a bad key **or** a bad signature. The body does not tell you which. Same response for an invented key.

Before you open a ticket:

1. Confirm you are on `https://gateway.bit2me.com` (no sandbox URL).
2. You are calling `POST /v1/signin/apikey`, not `/v1/signin/embed`.
3. You did **not** POST `{}` unless that object is also in the HMAC message.
4. The secret matches the key (copy both from the dashboard; trim `.env` whitespace).
5. Pass the [known-answer fixture](#known-answer-fixture). If the fixture fails, do not hit production.
6. `x-nonce` is **milliseconds** (`Date.now()`), within 5 seconds of UTC.

401 is still the usual HMAC / clock failure on most Wallet routes. See [Fix HMAC 401](/recipes/hmac-401) and [Errors](/guides/errors).

## TOTP

Some operations require 2FA:

- `x-totp` — code
- `x-totp-type` — `gauth` \| `sms` \| `email`

For **subaccount** operations, `x-totp-type` is always `gauth`.

Enroll subaccount 2FA with `POST /v1/account/subaccount/sfa` (`subaccountUserId` in JSON) then `PUT /v1/account/subaccount/sfa` (`subaccountUserId` + `totp` in JSON). Parent enroll is `POST` then `PUT /v1/account/settings/sfa`. Withdrawal 2FA still uses `x-totp` headers. Details: [2FA 420 and 428](/recipes/totp).

## Playground

Mintlify cannot compute this HMAC in the interactive playground. REST pages on this site use **copyable** examples. Sign locally, then send the request from your backend.

## Key scopes

When you create a key you can request:

- **Read**
- **Trade** — create or cancel orders
- **Withdraw** — withdrawals that bypass two-factor authentication

Prefer IP allowlists on Trade and Withdraw keys. Do **not** issue a Withdraw-scoped key for subaccount remittance if you need TOTP on every send — that scope is documented as bypassing two-factor authentication.

## Rotate a key

1. Open [Get API keys](https://account.bit2me.com/api-keys).
2. Create a **new** key (and secret). Store the secret outside the app logs.
3. Point your backend at the new pair.
4. **Revoke** the old key in the same dashboard.

There is no published dual-key grace window. Treat revoke as immediate. If a secret leaked, revoke first, then rotate.

## Gateway WebSocket

REST HMAC does not sign the notification socket. After `open` on `wss://${host}:${port}/` (host from Scalar / your integration manager):

- JWT: `POST /v1/signin/apikey` (HMAC) → send `{ "type": "authenticate", "payload": { "token": "<accessToken.token>" } }`
- Or API key: `{ "type": "authenticate", "payload": { "apikey": ["<api-key>"] } }`

Failed auth closes the socket with **4000**. Full examples: [Gateway notifications](/wallet/websocket).

Pro Trading uses a **different** URL and envelope (`event: authenticate` + REST token, 1 minute). See [Pro WebSocket](/pro/websocket).
